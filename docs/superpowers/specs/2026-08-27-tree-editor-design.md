# Design: Problem-Finder Tree Editor

**Date:** 2026-08-27  
**Status:** Approved  
**Location:** `/jvm-tools/` page, below the existing decision-tree widget

---

## Context

The decision tree lives in `data/jvm-tools/problem-finder.yaml`. Editing it by hand is workable but error-prone — typos in node IDs, dangling `next:` references, and structural mistakes are invisible until the site rebuilds. This editor provides a visual, in-browser way to modify the tree and export valid YAML.

**Scope:** Local dev tool. No authentication. No server writes. Export = clipboard copy. Paste into the YAML file yourself and rebuild.

---

## Architecture

### Data flow

```
Hugo build time:
  data/jvm-tools/problem-finder.yaml
         ↓  Hugo template embeds as JSON
  <script type="application/json" id="pf-tree-data">...</script>
         ↓  Alpine reads on mount
  treeEditor() Alpine component (reactive in-memory state)
         ↓  user edits
  SVG diagram  +  edit panel  (reactive, re-render on every change)
         ↓  "Copy YAML" button
  validate → serialize → clipboard
```

### Files

| File | Status | Responsibility |
|---|---|---|
| `themes/projects-theme/layouts/partials/problem-finder-editor.html` | **Create** | Hugo partial: embeds tree JSON, renders editor shell, mounts Alpine component |
| `themes/projects-theme/assets/js/tree-editor.js` | **Create** | Alpine component factory `treeEditor()`: state, diagram, validation, YAML serialization |
| `themes/projects-theme/assets/js/main.js` | **Modify** | Import `treeEditor` and register on `window` before `Alpine.start()` |
| `themes/projects-theme/layouts/collection/list.html` | **Modify** | Include `problem-finder-editor.html` after the existing widget include |

No changes to `main.css`, `config.yaml`, or any data file.

### No new dependencies

YAML serialization is hand-rolled (~60 lines). The SVG diagram is plain DOM elements generated by Alpine. No npm packages added.

## Hugo Partial

`problem-finder-editor.html` receives `.` (page context). It:

1. Reads `$tree := index site.Data "jvm-tools" "problem-finder"` (same as the widget partial)
2. Builds a `$toolIds` list from all three section static.yaml files (used to populate tool ID autocomplete suggestions in the editor)
3. Emits:

```html
<script type="application/json" id="pf-tree-data">{{ $tree | jsonify }}</script>
<script type="application/json" id="pf-tool-ids">{{ $toolIds | jsonify }}</script>

<div x-data="treeEditor()" x-init="init()" class="mt-16 border-t-2 border-dashed border-gray-200 pt-8">
  <!-- editor shell (header bar, diagram panel, edit panel) -->
</div>
```

The Alpine component is defined in `tree-editor.js` and registered as `window.treeEditor` before `Alpine.start()`.

## Alpine Component: `treeEditor()`

### State shape

```js
{
  // Raw tree: object keyed by node ID, values are node objects
  // Mirrors the YAML structure exactly
  nodes: {},          // { [id]: { type, text?, options?, headline?, tools?, followon?, related? } }
  nodeOrder: [],      // array of IDs in insertion order (for consistent YAML export)
  selected: null,     // currently selected node ID (string | null)
  errors: [],         // validation errors (array of strings)
  copied: false,      // "Copied!" feedback flag

  // SVG diagram layout (computed)
  svgNodes: [],       // { id, x, y, w, h, type, label }
  svgEdges: [],       // { x1, y1, x2, y2, label }
  svgWidth: 0,
  svgHeight: 0,
}
```

### Initialisation

`init()` reads the JSON blob from `#pf-tree-data`, parses it, and populates `nodes` and `nodeOrder`. Then calls `layoutDiagram()`.

### Diagram layout: `layoutDiagram()`

Performs a top-down BFS layout starting from `start`:

1. Assign each node a column based on BFS level (depth from `start`)
2. Stack nodes at the same depth vertically
3. Compute `svgNodes` (x, y, w, h for each box) and `svgEdges` (lines + truncated option labels)
4. Nodes not reachable from `start` (orphans) are appended in a column to the right labelled "Unreachable"

Node box sizes:
- Questions: 160×50px, blue border (`#3b82f6`), white fill
- Results: 160×50px, green border (`#22c55e`), white fill
- Selected: 2px highlight ring in the node's colour

Labels: first 22 chars of `text` / `headline`, truncated with `…`

Edge labels: first 18 chars of the option `.label`, truncated with `…`, rendered as small grey `<text>` elements midpoint on the edge line.

The diagram re-renders via a reactive `$watch('nodes', () => layoutDiagram())` watcher plus manual calls after any mutation.

### Interactions

**Select node:** click SVG node → `selected = id`, edit panel updates.

**Add question node:**
- Button "+ New question" in header bar
- Generates a unique ID: `q-new-1`, `q-new-2`, etc. (incrementing until unique)
- Adds `{ type: 'question', text: '', options: [] }` to `nodes`
- Appends ID to `nodeOrder`
- Selects it

**Add result node:** same pattern, prefix `r-new-`, `{ type: 'result', headline: '', tools: [] }`

**Delete node:**
- Confirmation inline (replace button text with "Sure?" for 2s, second click confirms)
- Removes from `nodes` and `nodeOrder`
- Also removes any option in any question node whose `next` points to the deleted ID (with a warning added to `errors` cleared on next validation run)
- Clears `selected` if it was the deleted node

**Reorder options:** drag-and-drop within the options list in the edit panel. Uses the `@dragstart` / `@dragover` / `@drop` Alpine event handlers on `<li>` elements (no external sortable library).

## Edit Panel

### Question node fields

| Field | Control | Notes |
|---|---|---|
| ID | `<span>` (read-only) | IDs are map keys; renaming would require updating all `next:` refs — not supported |
| Type badge | `<span>` | read-only, shows "question" |
| Text | `<textarea rows="2">` | live-updates `nodes[id].text` |
| Options | draggable `<li>` list | see below |

Each option row:
```
≡  [label text input____________]  → [next dropdown▾]  [✕]
```
- `≡` drag handle
- Label: `<input type="text">` bound to `option.label`
- `→`: dropdown `<select>` populated from `nodeOrder` (all node IDs), bound to `option.next`
- `✕`: removes the option

`[+ add option]` button appends `{ label: '', next: '' }`.

### Result node fields

| Field | Control |
|---|---|
| ID | read-only `<span>` |
| Type badge | read-only |
| Headline | `<textarea rows="2">` |
| Tools | list (see below) |
| Follow-on | collapsible section (see below) |
| Related | list of collapsible groups |

**Tool entry** (used in primary tools, follow-on tools, related tools):
```
ID: [input___________]  Section: [jvm-tools▾]
Note: [input_________________________________]  [✕]
```
- ID: text input (free text; suggestions from `$pf-tool-ids` via `<datalist>`)
- Section: `<select>` with options `jvm-tools`, `femto`, `experiments`
- Note: text input, optional
- `✕`: remove tool

`[+ add tool]` appends `{ id: '', section: 'jvm-tools', note: '' }`.

**Follow-on section:** toggle checkbox "Add follow-on callout". When checked, shows:
```
Heading: [input_____________________________]
Tools:   [same tool entry list as above]
```
When unchecked, clears `nodes[id].followon` from state.

**Related groups:** `[+ add related group]` appends `{ label: '', tools: [] }`. Each group:
```
Label: [input____________________________]  [✕ remove group]
Tools: [tool entry list]
[+ add tool to group]
```

## Validation

Runs automatically whenever "Copy YAML" is clicked. Errors are shown in a red panel above the button. The export is blocked if any error exists.

### Validation rules

| Rule | Error message format |
|---|---|
| `start` node exists | `Missing required 'start' node` |
| Every `option.next` points to an existing ID | `Option "{label}" in node "{id}" points to "{next}" which doesn't exist` |
| Every result `tools[].id` is non-empty | `Tool #{n} in result "{id}" has no ID` |
| No empty question `text` | `Question "{id}" has no text` |
| No empty option labels | `Option #{n} in "{id}" has an empty label` |
| No option `next` is empty string | `Option "{label}" in "{id}" has no target (set the → dropdown)` |
| Every question has ≥ 1 option | `Question "{id}" has no options` |
| Every result has ≥ 1 tool | `Result "{id}" has no tools` |
| No empty result `headline` | `Result "{id}" has no headline` |
| Follow-on heading non-empty when follow-on exists | `Follow-on in "{id}" has no heading` |
| Follow-on has ≥ 1 tool when follow-on exists | `Follow-on in "{id}" has no tools` |
| Related group label non-empty | `Related group #{n} in "{id}" has no label` |
| Related group has ≥ 1 tool | `Related group "{label}" in "{id}" has no tools` |

Duplicate IDs are structurally impossible (IDs are object keys).

## YAML Serialization

The serializer produces output that matches `problem-finder.yaml` exactly:

```
# Decision tree for the "Have a problem?" widget on /jvm-tools/
# Each key is a node ID. Two types: question (shows options) and result (shows tools).
# To add a tool: add a result node and wire an option in the relevant question to it.
# Start node is always "start".
# Optional result fields: followon (next steps), related (alternative paths).
# Tools may specify section: experiments|femto to link outside jvm-tools.

<nodes in nodeOrder, separated by blank lines>

# ── Result nodes ──────────────────────────────────────────────────────────────

<result nodes in nodeOrder>
```

Rules:
- `start` always emitted first, then remaining questions, then results (matching file convention)
- Strings containing `:`, `#`, `'`, or `"` are double-quoted
- Strings with apostrophes use double quotes
- Multi-word strings with no special chars are unquoted
- Indentation: 2 spaces per level
- No trailing spaces

## Layout: Editor Shell

```
┌─────────────────────────────────────────────────────────────────────┐
│  🌳 Tree Editor                                                      │
│  Edit below, then Copy YAML and paste into                          │
│  data/jvm-tools/problem-finder.yaml and rebuild.                    │
│                                                                     │
│  [+ New question]  [+ New result]              [Copy YAML ▸]        │
├──────────────────────────────────┬──────────────────────────────────┤
│  DIAGRAM                         │  (select a node to edit)         │
│  (SVG, scrollable)               │                                  │
│  …                               │  …                               │
└──────────────────────────────────┴──────────────────────────────────┘
```

- Left panel: min-height 500px, overflow scroll, SVG fills available space
- Right panel: scrollable form, appears when `selected !== null`; shows placeholder text when nothing selected
- On mobile (`< md`): stacked vertically — diagram on top, edit panel below
- Validation error panel: red box between toolbar and split panels, only visible when `errors.length > 0`

## What this does NOT do

- Does not write to `problem-finder.yaml` directly (static site, no server)
- Does not rename node IDs (too risky without a rename-all operation)
- Does not support undo/redo (out of scope)
- Does not run `hugo build` or live-preview the widget output
