# Distributed Tool YAML Design

**Date:** 2026-09-07  
**Status:** Draft

---

## Context

Currently all tool metadata (taglines, install instructions, usage examples, feature lists, etc.) lives in three large central YAML files in the website repo:

- `data/jvm-tools/static.yaml` (17 tools, 740 lines)
- `data/femto/static.yaml` (5 tools)
- `data/experiments/static.yaml` (6 tools)

**Problem:** When a tool changes — new install instructions, updated tagline, new usage example — the author must open a PR against the *website* repo rather than the *tool* repo. The website repo becomes a bottleneck and the metadata drifts out of sync with the actual tool. The website also owns `group` assignments (what category a tool appears in), which is correct, but `group` is currently a freeform string embedded inside each tool entry rather than a structured registry.

**Goal:** Move per-tool metadata into each tool's own GitHub repo as a `.tool.yaml` file. The website repo retains a `data/categories.yaml` that controls collection membership, grouping, and ordering. A fetch script assembles the final `static.yaml` at build time; Hugo templates and the release-fetch pipeline need no changes.

---

## Architecture

```
Each tool repo (e.g., github.com/parttimenerd/jstall)
  └── .tool.yaml                       ← tool author owns this

Website repo (parttimenerd.github.io)
  └── data/categories.yaml             ← website owns collection/group structure
  └── scripts/fetch_tool_metadata.py   ← new; fetches .tool.yaml per repo, writes static.yaml
  └── data/<collection>/static.yaml    ← regenerated by CI, committed to repo (same as releases.json)
  └── data/<collection>/releases.json  ← unchanged (auto-fetched by fetch_releases.py)
```

Hugo templates and `fetch_releases.py` are **unchanged** — they continue reading `data/<collection>/static.yaml` in the same format as today.

`static.yaml` is regenerated by CI and committed back to the repo on every run — identical to how `releases.json` works today. The deploy workflow (`deploy.yml`) reads data files from the checked-out repo, so they must be committed. `static.yaml` is not hand-edited; the CI commit is the only writer.

## 1. `.tool.yaml` Schema

File lives at the **root** of each tool repo. The `id` is derived from the repo name (never written in the file). The `group` is assigned by `categories.yaml` (never written in the file).

### Required fields

```yaml
tag: ready | experimental | poc | demo
tagline: string          # 1–2 sentences shown in detail view
tagline_short: string    # ≤ 10 words shown on cards and in nav tooltip
```

### Optional — source control

```yaml
github_url: string       # Full URL; defaults to the repo URL this file was fetched from
github_pages: string     # Docs or web-app URL; shows "Docs"/"Web app" link
```

### Optional — release resolution

```yaml
maven_coordinates: "groupId:artifactId"
cargo_crate: "crate-name"
static_version: string   # Hard-coded version when no release source exists
no_release: true         # Skip this entry in fetch_releases.py entirely
```

### Optional — content/display

```yaml
screenshot: string       # URL; shown with lightbox in detail view
when_to_use:
  - string               # Green ✓ bullet points
when_not_to_use:
  - string               # Red ✗ bullet points
features:
  - string               # Alternative to when_to_use for demo/poc entries
vs:
  name: string           # Other library/tool name
  url: string            # Link to the other tool
  self_label: string     # Column header for this tool (defaults to tool id if absent)
  bottom_line: string    # One-liner picking guidance
  comparison:
    - feature: string
      self: string       # This tool's value
      other: string      # Other tool's value
related:
  - label: string
    url: string
links:
  - label: string
    url: string
install:
  - label: string        # Tab label (e.g., "Maven", "Gradle")
    lang: string         # Code block language
    code: |              # VERSION is substituted with resolved release version
      ...
usage:
  - label: string
    lang: string
    code: |              # VERSION is NOT substituted
      ...
note: string             # Shown as amber callout at the bottom
```

### Optional — new fields

```yaml
license: string          # SPDX identifier, e.g. "Apache-2.0", "MIT"

# tag describes maturity/stability of the code.
# maintenance_status describes the author's ongoing commitment to the project.
# They are independent: a tool can be tag:ready but maintenance_status:archived.
maintenance_status: maintained | archived | seeking-maintainers
# Omit if the tool is actively maintained (the default assumption).

platform_support:
  - os: linux | macos | windows
    note: string         # Optional per-platform caveat, e.g. "amd64 only"
# Omit entirely if the tool is platform-agnostic (pure JVM, pure Java, etc.).
```

### Fields never in `.tool.yaml`

| Field | Owner | Notes |
|---|---|---|
| `id` | Derived | Last path segment of repo URL from `categories.yaml` |
| `group` | `categories.yaml` | Website controls visual grouping |
| `no_sap` | `categories.yaml` | Website-side filter for SapMachine page |

## 2. `data/categories.yaml` Schema

Replaces hand-edited `static.yaml` files as the source for collection/group structure. This file is the only place where "what tools exist and how they're grouped" is declared.

```yaml
collections:
  - id: jvm-tools           # Matches existing data/ section slug and URL
    title: "JVM Tools"
    groups:
      - name: "Live JVM Inspection"
        tools:
          - repo: https://github.com/parttimenerd/jstall
          - repo: https://github.com/parttimenerd/condensed-data

      - name: "JFR / Profiling"
        tools:
          - repo: https://github.com/parttimenerd/jfr-query
            no_sap: true    # Website-side filter: exclude from SapMachine listing
          - repo: https://github.com/parttimenerd/jfr-profiling

      - name: "Learning Resources"
        tools:
          - repo: https://github.com/parttimenerd/writing-a-profiler
        fallback_tools:     # Third-party or uncontrolled repos: metadata defined inline
          - id: some-external-tool
            tag: ready
            tagline: "..."
            tagline_short: "..."
            # ... any .tool.yaml fields; id is required here since it can't be derived

  - id: femto
    title: "Femto Libraries"
    groups:
      - name: "Libraries"
        tools:
          - repo: https://github.com/parttimenerd/femtolz4
          - repo: https://github.com/parttimenerd/femtocli

  - id: experiments
    title: "Experiments"
    groups:
      - name: "eBPF"
        tools:
          - repo: https://github.com/parttimenerd/hello-ebpf
```

**Key rules:**
- A tool entry's `id` = last path segment of `repo:` URL (e.g., `jstall`)
- `no_sap: true` on a tool entry is a website-side flag; the tool repo never sees it
- `fallback_tools` live **inside a group**, not at the collection level — so their group assignment is unambiguous
- `fallback_tools` entries require an explicit `id` (since there's no repo URL to derive it from) and accept all `.tool.yaml` fields

## 3. `fetch_tool_metadata.py` Script

New script: `scripts/fetch_tool_metadata.py`

**Inputs:** `data/categories.yaml`  
**Output:** `data/<collection-id>/static.yaml` for each collection (same format as today)  
**Called before:** `fetch_releases.py`

### Algorithm

```
For each collection in categories.yaml:
  tools = []
  For each group in collection.groups:
    For each tool_entry in group.tools:
      id = last_path_segment(tool_entry.repo)
      raw_url = "https://raw.githubusercontent.com/<owner>/<repo>/HEAD/.tool.yaml"
      yaml_data = fetch(raw_url, GITHUB_TOKEN)
      if fetch fails (404, network error, parse error):
        WARN with repo URL and reason; skip this tool
      else:
        validate required fields (tag, tagline, tagline_short)
        if validation fails: WARN naming the missing fields; skip this tool
        merged = yaml_data + {id, group: group.name, no_sap: tool_entry.no_sap or false}
        tools.append(merged)
    For each fallback_tool in group.fallback_tools:
      tools.append(fallback_tool + {group: group.name})
  write_static_yaml(collection.id, tools)
```

### Behavior details

- Uses `GITHUB_TOKEN` env var (same pattern as `fetch_releases.py`)
- Missing `.tool.yaml` (HTTP 404): warn with repo URL, skip tool
- Invalid YAML syntax: warn with parse error, skip tool
- Missing required fields: warn naming the missing fields, skip tool
- Network failure: warn, skip tool — build continues with partial results
- **Exit code 0** even with warnings — partial output is better than no output
- **Exit code 1** only if `data/categories.yaml` itself is missing or unparseable
- Output `static.yaml` uses the same schema comment header as today's files
- No on-the-fly field renaming — `.tool.yaml` files in tool repos use `self:` from the start (see migration §5)

## 4. CI Changes

### `update-all.yml`

Add a new `fetch-metadata` job. The existing `releases` jobs gain `needs: [fetch-metadata]` so they always run after metadata is assembled (they need the `static.yaml` to know which tools to fetch releases for):

```yaml
fetch-metadata:
  name: Fetch tool metadata
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: '3.x'
    - run: pip install requests pyyaml
    - run: python scripts/fetch_tool_metadata.py
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    - uses: actions/upload-artifact@v4
      with:
        name: static-yaml-data
        path: |
          data/jvm-tools/static.yaml
          data/femto/static.yaml
          data/experiments/static.yaml
```

The `commit` job downloads `static-yaml-data` alongside `releases-data` and commits all together — same pattern as `releases.json` today.

### `update-jvm-tools.yml`

Add a `fetch_tool_metadata.py` step before the existing `fetch_releases.py` step. The script accepts an optional `--section jvm-tools` flag to fetch only that collection (faster, fewer API calls for a per-tool triggered run).

## 5. Migration Plan (Big-Bang)

28 tools total: 17 jvm-tools + 5 femto + 6 experiments.

### Step 1 — Write and test `scripts/fetch_tool_metadata.py`

Implement the script. Test it locally *before* touching any tool repos by pointing it at the current `static.yaml` files as a baseline: run it, confirm it doesn't crash, confirm the `data/categories.yaml` parsing works.

### Step 2 — Create `data/categories.yaml`

Build from the existing `static.yaml` files, preserving group assignments and `no_sap` flags. Verify the YAML is valid and all 28 tools are listed.

### Step 3 — Create `.tool.yaml` in each tool repo

For each tool, copy fields from its current `static.yaml` entry:
- Drop: `id`, `group`, `no_sap`
- Rename: `femto:` → `self:` in any `vs.comparison` entries (do this in the tool repo, not in the fetch script)
- Add new optional fields where applicable: `license`, `platform_support`, `maintenance_status`

Tools:
- **jvm-tools** (17): jstall, cf-cli-java-plugin, jfr-profiling, firefox-profiler, jfr-query, condensed-data, jfrevents, tiny-profiler, hprof-analyzer, hprof-redact, jhserr, jdklogs, test-order, execjar, meta-agent, jthreaddump, writing-a-profiler

- **experiments** (6): hello-ebpf, concurrency-fuzz-scheduler, taskcontrol, sound-of-scheduling, check-language-version, local-android-ai

### Step 4 — Update Hugo template for `vs` columns

Update `themes/projects-theme/layouts/collection/list.html` to read `self:` instead of `femto:` in comparison tables, and use `self_label` (defaulting to tool `id`) as the column header. Do this *before* the verification step so `hugo serve` renders comparison tables correctly.

### Step 5 — Run fetch script and verify against old files


Output should match the old `static.yaml` files modulo: dropped `id`/`group`/`no_sap` from the YAML keys (they're still present — id and group are merged in by the script), `femto:` → `self:` in comparison rows, and any new optional fields added.

### Step 6 — Update CI and delete old files

- Add `fetch-metadata` job to `update-all.yml`
- Add `--section` support and fetch step to `update-jvm-tools.yml`
- Delete old hand-edited files: `git rm data/jvm-tools/static.yaml data/femto/static.yaml data/experiments/static.yaml`
